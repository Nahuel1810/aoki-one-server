## Conocimiento empirico extraido (NO se puede re-derivar leyendo codigo)

- Gramatica exacta de locationCode (regex viva): /^([A-Z0-9]+)(\d{2})A([A-L])(\d)([TDL])?$/ = <estanteria alfanumerica libre><modulo 2 digitos>A<nivel 1 letra A-L><posicion 1 digito>[T|D|L opcional]. La 'A' entre modulo y nivel es un separador literal, no parte del nivel.
- Entrada normalizada antes de parsear: String(input).trim().toUpperCase(). El parser acepta minusculas y espacios.
- Nivel: letra -> numero = charCodeAt - 'A'.charCodeAt + 1, es decir A=1, B=2, C=3, ... L=12. Doce niveles exactos. Fuera de A-L lanza Error("Nivel invalido. Debe ser entre A y L").
- Lado por paridad del modulo: modulo PAR -> sideBit 0 -> side "RIGHT" (derecho); modulo IMPAR -> sideBit 1 -> side "LEFT" (izquierdo). Verificado con modulo 04 (sideBit 0) y modulos 05 y 03 (sideBit 1).
- actionBit: "T" (traer) = 1, "D" (devolver) = 0. El sufijo "L" se normaliza a "D" (mismo actionBit 0). Sin sufijo, action = null y el actionBit lo debe imponer el llamador.
- Comando de carro = string `${posicion}${parante:2digitos}${sideBit}${actionBit}` y commandCode = Number(ese string). El primer digito es la posicion, por lo que una posicion 0 colapsaria el numero (no existe posicion 0 en planta).
- parante = Math.ceil(modulo / 2), formateado con padStart(2, "0"). Modulos 03 y 04 comparten parante "02" y se distinguen solo por el ladoBit.
- Casos borde concretos verificados contra el robot real: "3X04AA3T" -> carro 30201; "3X04AA3" + override D -> carro 30200; "3X03AA1T" -> carro 10211; "3X04AC3T" -> elevador 103; "3X05AL1D" -> nivel 12, sideBit 1, actionBit 0.
- Elevador ir-a-nivel = 100 + nivelNumerico (nivel A -> 101 ... nivel L -> 112). Variante en plcProtocol.buildElevadorIrNivel que clampea el nivel a 0..99 antes de sumar.
- Elevador set-nivel (calibracion) = 500 + nivel, tambien clampeado a 0..99.
- baseCode (identidad de ubicacion, sin accion) = `${estanteria}${modulo}A${nivelLetra}${posicion}`. Es la clave con la que se compara una ubicacion contra otra ignorando el sufijo T/D/L.
- Mapeo estanteria->robot hoy vigente: "3X" -> "1" (hardcodeado). Sin mapeo explicito, robotId = el propio codigo de estanteria en mayusculas (permite prefijos arbitrarios: 3Y, 4X, RACKA1).
- plcProtocol CARRO.COMMANDS: INIT 41000, PUENTE_DER 50000, PUENTE_IZQ 51000, EXECUTE_LIST 90000. CARRO.SUCCESS = 100.
- plcProtocol ELEVADOR.COMMANDS: QUERY_LEVEL 200, QUERY_CAR_PRESENCE 300, INIT 400, EXECUTE_LIST 900. ELEVADOR.SUCCESS = 100.
- Decodificacion de respuesta del PLC: 100 -> OK; 101-199 -> ERROR con errorCode = valor - 100; 200-299 -> LEVEL con level = valor - 200; 300 -> CAR_PRESENT; 301 -> CAR_ABSENT; cualquier otro -> UNKNOWN.

## Mapeo test por test

### [ADAPTADO] tests/unit/locationTranslator.test.js :: parsea ubicacion con accion traer
- **Comportamiento**: Parsea "3X04AA3T": modulo "04" (par) -> sideBit 0, nivel A -> 1, posicion 3, sufijo T -> action "T" y actionBit 1; ademas resuelve robotId "1" desde la estanteria "3X".
- **Empirico**: True | **RF**: RF01
- **Destino**: `packages/domain/src/locationCode.test.ts`
- **CAMBIO DE CONTRATO**: Cae el assert `parsed.robotId === "1"`. RF01 enumera lo que deriva el parseo (baseCode, estanteria, modulo, lado, nivel, posicion) y no incluye robotId; el mapeo estanteria->robot pasa a la tabla `robots(site_id, estanteria_code)` de RF23, y el RNF de Calidad exige `domain/` puro (un mapa de despliegue hardcodeado no puede vivir ahi en un sistema multi-sucursal). Los otros 6 asserts (moduleCode, sideBit, levelNumber, position, action, actionBit) se portan literales. Se agrega assert de `baseCode` y de `side === "RIGHT"`, que el legacy no verifica.
- **Calidad del test legacy**: Mezcla dos responsabilidades en un solo test: la gramatica del codigo (empirica) y la resolucion de robot por despliegue (configuracion). El assert de robotId no prueba nada de la gramatica y es el unico que ata el test a un mapa hardcodeado.

## CORRECCIONES DE LA AUDITORIA CRUZADA (tienen prioridad sobre el mapeo de arriba)

- Incoherencia dentro del mismo archivo y misma regla: `parsea ubicacion con accion traer` está marcado ADAPTADO y su gemelo `parsea ubicacion con accion devolver` DIRECTO. Afirman lo mismo (parseo + derivación de lado/nivel/posición + robotId) y RF01 no cambia nada de ese contrato. Uno de los dos veredictos está mal y, además, el que dice 'adaptado' no dice qué assert cambia — el criterio lo exige.
- `mapeo de estanteria a robot configurable` → TRADUCIDO a RF23 es el RF equivocado: RF23 es persistencia SQLite, no resolución de robotId. Peor, el test de `accion traer` manda la MISMA regla (estantería 3X → robot 1) a RF01/dominio. Dos analistas mandan la misma pieza de conocimiento a dos destinos distintos. Y el veredicto correcto es ADAPTADO, no traducido: el fallback identidad ('4X'→'4X') no sobrevive a un esquema donde `robots(id, site_id, estanteria_code)` separa el id del código de estantería.
- `orchestrator :: no duplica orden si llega el mismo id externo` [ADAPTADO, RF14] y `api :: /api/orders/pick deduplica por id numerico` [TRADUCIDO, RF26] prueban el MISMO invariante con veredictos y destinos incompatibles: uno se queda en el agente, el otro se va al servidor. Ambos deben decir lo mismo: la clave pasa de `id` numérico a `(siteId, externalOrderId)`, el agente conserva su índice único local (RF14) y el ingreso de picking se va al servidor (RF26). Tal como está, el primero no justifica por qué es 'adaptado' (el comportamiento no cambió) y el segundo no dice que el endpoint desaparece de la API local.
- `errorHandler :: clasifica errores retryables` [ADAPTADO] está subestimado: no es un cambio de contrato, es la regla INVERTIDA. Legacy = reintentable por default, fatal solo por opt-in (`error.fatal===true`). RF19 = solo los de transporte se reintentan, todo lo demás falla rápido. Y el mismo test se convierte en el punto de partida del health profundo de RF25 (conectividad, cola, enlace), cosa que el veredicto no enuncia.
- `slotDistance :: solo considera slots libres` [ADAPTADO] no dice qué cambia. Lo que cambia con uniones discriminadas es concreto: desaparecen el alias 'AVAILABLE', el matcheo case-insensitive y el 'sin status se asume LIBRE'. O se declara eso, o el veredicto correcto es DIRECTO.
- Nota transversal sobre los dos tests de reintentos (`marca error cuando agota retries` y `ErrorHandler calcula backoff`, ambos DIRECTO): bajo el RNF de deadlines por paso y por orden, agotar maxRetries deja de ser la única condición de salida. Los tests siguen pasando, pero portarlos como 'directo' sin agregar el caso de deadline deja la nueva dimensión del contrato sin ninguna verificación.

## RF sin cobertura (deficit conocido -> T24/T25, NO es alcance de T02)

- **[alto] RF11** Resolución de destino de PUT: Ningún test cubre lo único que RF11 realmente pide: destino = currentBox.sourceLocationCode cuando el slot tiene cajón en libros. El legacy NUNCA lee sourceLocationCode para el destino (resolveStepCommand usa `target || source`, y para PUT `source` es el propio slot), así que si falta targetLocation devuelve el cajón al mismo slot. Los dos assert nuevos —targetLocation obligatorio con 400 si el slot está vacío en libros, e ignorado si tiene cajón— y la prohibición de devolver al propio slot no existen en ningún test portable. Es comportamiento nuevo sobre el camino físico del robot.
- **[alto] RF09** Orden de servicio: FIFO + PICK antes que PUT, con inversión por zona llena: El único test que cita RF09 (`QueueManager mantiene FIFO por robot`) solo prueba FIFO. Ni la prioridad PICK>PUT ni la inversión cuando la zona de pickeo de ese lado está llena tienen test. Es la regla que reemplaza a `priority` (eliminado del modelo) y la única defensa contra el deadlock de un PICK encabezando la cola sin slots libres. Se escribe de cero, sobre un robot en producción, sin red.
- **[alto] RF13** El slot conserva su estado tras fallo de paso, y deadlines por paso y orden: El legacy hace exactamente lo contrario: ante un paso fallido llama `blockSlot(...)` y deja el slot en ERROR. RF13 dice que conserva RESERVADO/OCUPADO y que ERROR queda solo para slots inutilizables. Ese blockSlot no tiene ningún test, así que la suite portada no va a detectar ni el comportamiento viejo ni el nuevo. Los deadlines por paso y por orden (RNF explícito: hoy un paso puede tardar minutos sin que nadie lo corte) tampoco tienen test.
- **[alto] RF10** Espera por slot: sin perder el lugar, por evento y FIFO por (robot, lado): Los tests solo afirman `waitingForSlot=true` y que el robot se libere. Lo que RF10 agrega no está cubierto: que la orden NO pierda su lugar (el legacy hace clearActive + enqueue, la manda al final), que se reactive por evento al liberarse un slot de ese lado (hoy espera al tick de 300 ms, y `POST /api/slots/:code/release` ni siquiera despierta al robot) y que la espera sea FIFO por lado, de modo que una orden esperando el lado izquierdo no bloquee a una del derecho.
- **[alto] RF03** Tabla completa de códigos y errores del PLC por dispositivo: De todo el protocolo solo hay test para el error 1 (reintentable) y el 99 (fatal). Sin cobertura quedan: 100=OK, el rango 200-299 de nivel, 300/301 de presencia de carro, UNKNOWN, y las dos tablas ERROR_CODES completas (9 entradas de CARRO, 8 de ELEVADOR). Es la tabla que sale de planta y es lo que lee el operario cuando el robot se traba.
- **[alto] RF07** Decremento de pendingReturns: solo el último PUT hace la devolución física: Hay test para la mitad de arriba (PICK sobre un cajón ya en slot → DONE sin maniobra) y para el refcount a nivel StateManager, pero ninguno para la mitad de abajo: PUT con pendingReturns>1 decrementa y termina DONE sin maniobra. Sin ese test, un port puede hacer que el primer PUT devuelva el cajón físicamente y deje al segundo pedido sin atender — que es literalmente el motivo por el que existe el refcount.
- **[alto] RF34** Outbox de transiciones y drenado ordenado al reconectar: Cero cobertura: el componente no existe en el legacy. Es el único mecanismo que garantiza que ningún cambio de estado se pierde por una caída de red, y el orden del drenado es lo que hace que el servidor no aplique transiciones desordenadas. Se escribe sin ninguna referencia empírica.
- **[alto] RF28** Entrega por long-poll con lease y re-entrega por vencimiento: Los dos tests que citan RF28 son de dedupe por id externo del agente, no de long-poll ni de leases. El lease vencido genera una re-entrega que solo el dedupe del agente (RF14) absorbe: si esa cadena falla, el robot hace la maniobra física dos veces. No hay nada que lo verifique.
- **[alto] RF29** Reporte de transiciones idempotente y por secuencia monótona: Sin cobertura. Con outbox + reintentos, los reportes repetidos y fuera de orden son el caso normal, no el excepcional. Si el servidor aplica un reporte viejo, la app de picking ve una orden retroceder de estado.
- **[alto] RF22** Dos niveles de autorización en la API local y bind a la IP de LAN: Ningún test toca autorización. El modelo nuevo apoya toda la seguridad del agente en que el listener bindee a la IP de LAN (HTTP_BIND) y en un token de mantenimiento para el comando directo a PLC — el único endpoint que escribe registros Modbus salteándose el orquestador y las máquinas de estado. Hoy el test de comando directo pasa sin credencial y un bind a 0.0.0.0 por descuido no falla ningún test.
- **[alto] RF06** Transiciones de slot inválidas como error del dominio: Los tests pinean los estados y las reservas, pero el legacy devuelve `null` en silencio ante una transición inválida (reserveSlot, reserveSlotForPut, reserveOccupiedSlotForPut). RF06 exige que sea error del dominio, no un estado silencioso. Portados literales, esos tests siguen pasando con el null y el requisito no se cumple nunca.
- **[alto] RF26** Ingreso de pedidos con HMAC + timestamp y validación de siteId: Sin cobertura. El único test de dedupe (`/api/orders/pick`) es por id numérico en el agente; RF26 pide clave compuesta `(siteId, externalOrderId)`, firma HMAC del body, anti-replay por timestamp y que una sucursal no pueda crear órdenes de otra. Es el único componente expuesto a internet.
- **[alto] RF33** Espejo local: orden persistida antes de ejecutarse: Sin cobertura. Es el invariante que hace que la ejecución nunca dependa del enlace; si se rompe, una orden reclamada y perdida en un reinicio deja el cajón a mitad de camino sin registro.
- **[medio] RF04** Secuencia física de 5 pasos y comando de cada paso: Solo hay verificación indirecta: el e2e cuenta 5 pasos y `/simulate` afirma stepCommands no vacío. Sin test unitario quedan el orden exacto HOMING→ELEVADOR(origen)→CARRO_BUSCA→ELEVADOR(destino)→CARRO_DEJA|CARRO_DEVUELVE, que el paso 4 use el nivel del DESTINO y no el del origen, y que el paso 5 cambie según PICK/PUT. Son cinco movimientos reales del robot.
- **[medio] RF23** SQLite como fuente de verdad con escrituras incrementales: Los tests de StateManager pinean lo contrario: snapshot completo en memoria persistido entero. El RF elimina ese volcado (RNF: `getSnapshot()` en cada step) y pide repositorios por entidad. Ningún test afirma que la fuente de verdad sobrevive al reinicio leyendo de SQLite ni que no se serializa el estado completo por paso.
- **[medio] RF25** /health profundo: El test actual solo verifica `{ok:true, mode:'simulation'}`. RF25 pide conectividad por dispositivo, profundidad de cola por robot, última orden completada, timestamp de arranque y estado del enlace con el servidor. Sin lo último el front no puede distinguir 'sin conexión con el servidor de pedidos' de 'el robot está caído', que es exactamente lo que la spec le promete a la UI.
- **[medio] RF27** Cola durable por (siteId, robotId) con histórico de transiciones: Sin cobertura. Debe sobrevivir a reinicios de servidor y de agente por separado; los dos casos de reinicio cruzado son justo donde aparece la pregunta de quién gana entre los dos libros.
- **[medio] RF32** Autenticación agente↔servidor por credencial de sucursal: Sin cobertura. Incluye el invariante de que el servidor nunca abre una conexión hacia la sucursal — que es lo que permite retirar VSCode Ports. Un test de arquitectura sería barato y hoy no existe.
- **[medio] RF35** Órdenes locales sin enlace, con externalOrderId prefijado por agente: Sin cobertura. El prefijo por agente es lo que evita que un id generado localmente colisione con uno de picking y termine deduplicando dos órdenes distintas en una. Es un choque silencioso: no falla, simplemente se pierde un pedido.
- **[medio] RF36** Degradación explícita sin modo silencioso: Sin cobertura. Los dos tests que citan RF36 son sobre montar/desmontar el router HTTP y sobre el modo simulación, nada que ver con el estado del enlace. El requisito es que no exista modo silencioso: o está sincronizado o lo dice.
- **[medio] RF37** Backoff con jitter y techo en el long-poll: Sin cobertura. Existe el test de backoff exponencial del ErrorHandler y el del monitor Modbus, pero ninguno de los dos tiene jitter ni aplica al enlace. Sin jitter, N agentes en Fase 2 sincronizan sus reintentos contra un servidor que vuelve.
- **[medio] RF21** Endpoints de la API local que ningún test toca: De los 18 endpoints actuales, la suite cubre 8. Sin ningún test quedan: retry, cancel, pausa y reanudación de cola, `GET /api/orders/:id`, `GET /api/orders/metrics/report` y `GET /api/devices/robots` — este último con un bug ya identificado en la spec (devuelve `{}` en `queue` con driver externo por una Promise sin await). Retry y cancel son las dos acciones con las que el operario destraba el robot.
- **[medio] RF24** Métricas por orden con reporte filtrable por rango de fechas: `recordOrderMetrics` calcula waitingMs y durationMs con reglas propias (startedProcessingAt con fallback a finishedAt, clamps a 0) y no hay un solo test sobre eso ni sobre el filtro por fechas. Es el dato con el que se mide si el robot mejoró.
- **[medio] RF20** SIMULATE_PLC con default false: Los tests fijan `simulatePlc=true` explícitamente, así que ninguno detecta el default. Hoy el default es `true` (`process.env.SIMULATE_PLC || 'true'`): arrancar sin configuración simula en silencio y el robot no se mueve mientras la API responde ok. Un test de una línea sobre el default no existe.
- **[medio] RF01** Rechazo de formatos inválidos y sufijo L: Los tests solo ejercitan dos códigos válidos con sufijo T y D. Sin cobertura: el rechazo de formatos inválidos que RF01 exige, el nivel fuera del rango A-L, y que el sufijo `L` se normalice a `D` (RF01 nombra [T|D|L] pero nadie fija que L≡D). El parseo es la puerta de entrada de todo el sistema.
- **[bajo] RF30** Consulta de estado de orden por externalOrderId para picking: Sin cobertura. Es el único contrato que la app de picking consume del servidor además del alta; no hay riesgo físico, pero sí de romper al consumidor en el cutover.
- **[bajo] RF31** Heartbeat y detección de sucursal caída: Sin cobertura. Riesgo acotado en Fase 1 con una sola sucursal, pero es la base de la operación en Fase 2.

## Conocimiento en riesgo (vive solo en el codigo legacy, sin test que lo proteja)

- COLISIÓN DE TABLAS DE ERROR CARRO/ELEVADOR (src/config/plcProtocol.js). `decodeResponse` resuelve el mensaje con `CARRO.ERROR_CODES[c] || ELEVADOR.ERROR_CODES[c]` sin saber qué dispositivo respondió. Los códigos 1, 2, 17, 18 y 99 existen en AMBAS tablas con significados distintos: 1 = 'Carro trabado avanzando' vs 'Elev trabado subiendo'; 17/18 = obstáculo del carro vs límite inferior/superior del elevador. O sea que hoy todo error del elevador se le muestra al operario con el texto del carro. Ningún test lo toca. En el dominio nuevo con uniones discriminadas la decodificación DEBE recibir el deviceType; si se porta la firma tal cual, se porta el bug.
- Tablas de comandos del PLC sin ningún test: CARRO PUENTE_DER 50000, PUENTE_IZQ 51000, EXECUTE_LIST 90000; ELEVADOR QUERY_LEVEL 200, QUERY_CAR_PRESENCE 300, INIT 400, EXECUTE_LIST 900; y `buildElevadorSetNivel` = 500 + nivel (distinto de ir-a-nivel = 100 + nivel). De todo el protocolo solo están pineados CARRO.INIT 41000 (indirecto, vía el test de split) y 100+nivel. Ambos builders de elevador además clampean el nivel a [0,99] en silencio.
- EL SPLIT HIGH/LOW DEL CARRO ESTÁ CUBIERTO A MEDIAS — respuesta directa a la advertencia de la spec. El test `ConnectionService resetea messageIn1 y messageIn2 para CARRO` verifica el RESET (escribe 0 en reg y reg+1) y menciona 41000 → 4 / 1000, pero NINGÚN test ejercita la regla aritmética de `splitCarroCommandValue`: `String(trunc(v)).padStart(5,'0').slice(-5)`, high = dígito[0], low = Number(dígitos[1..4]). NO es un split de 16 bits: es un split DECIMAL a 5 dígitos. Un comando de carro como 30201 va a high=3, low=201. Reimplementarlo como `v>>16` / `v & 0xFFFF` compila, pasa el type-check y manda al carro a otro parante. Además `slice(-5)` trunca en silencio valores de más de 5 dígitos y un valor no finito lanza 'Comando de carro invalido'. Es el caso borde exacto que la spec pide proteger y está sin pinear.
- ESPACIOS DE REGISTRO DISTINTOS EN LA MISMA DIRECCIÓN. `messageIn` se ESCRIBE como holding register (writeRegister, FC06) y `messageOut` se LEE como input register (readInputRegisters, FC04) — y el mapa por defecto (src/config/deviceRegisterMaps.js) pone AMBOS en la dirección 0. Coinciden en número y no en espacio de direcciones. Un port que unifique todo en holding registers compila, pasa todos los tests con fakes y no habla con el PLC. `readDeviceState` lo confirma: lee messageIn con readHoldingRegisters (2 registros si es CARRO, 1 si no) y messageOut con readInputRegisters. Ningún test lo cubre porque todos usan dobles del cliente.
- CONFIG MUERTA QUE CONTRADICE EL MAPA REAL: `.env.example` documenta MODBUS_COMMAND_REGISTER=0, MODBUS_VERIFY_REGISTER=1 y MODBUS_RESPONSE_REGISTER=2 — tres variables que el código NO lee en ninguna parte (el mapa real son `messageIn`/`messageOut` de deviceRegisterMaps, ambos en 0). Quien reescriba mirando el .env.example va a cablear el registro de respuesta en la dirección 2 en vez de la 0 y a inventar un 'verify register' que no existe.
- EL TUNING DE PLANTA VIVE SOLO EN EL .env, NO EN EL CÓDIGO. Los defaults del código son STEP_ACK_INTERVAL_MS=2000 / 60 intentos y STEP_RESET_INTERVAL_MS=2500 / 60. El .env real de la sucursal los baja a 150 ms / 600 intentos en ambos casos, con el comentario 'mismo techo (~90 s), menor latencia'. El RNF de la spec dice 'se mantiene el polling de messageOut a 150 ms' — un port escrito mirando los defaults del código multiplica por 13 la latencia percibida de cada maniobra. Ningún test fija ni el intervalo ni el techo. El .env también lleva ORCHESTRATOR_TICK_MS=300 y BASE_BACKOFF_MS=200 (el código default es 500).
- ESCALERA DE RECUPERACIÓN MODBUS COMPLETA, casi sin test (`_runModbusOpInner`): 3 intentos internos separados por 2000 ms (MODBUS_CONNECTIVITY_INNER_ATTEMPTS/DELAY_MS) → recrear cliente → hasta 10 rondas (MODBUS_HARD_RESET_AFTER_RECREATES_PER_DEVICE) → hard reset con cooldown de 1000 ms → opcionalmente `process.exit(1)` (MODBUS_HARD_RESET_EXIT_PROCESS) para que PM2/systemd reinicie. Solo el hard-reset final tiene test. Peor caso: 10 × 3 × 2 s = 60 s POR OPERACIÓN Modbus — y `waitForExpectedResponse` invoca una operación por cada uno de sus 600 ciclos. De ahí sale el '90 s de ACK + hasta 66 s de reintentos' del RNF, y por eso el techo real de un paso no está acotado por nada.
- BACKOFF DEL MONITOR, SEPARADO DEL DE LOS STEPS: base 2000 ms, `min(base · 2^(n-1), 30000)` con techo de 30 s, y recreación de cliente cuando `consecutiveFailures % 5 === 0` (módulo, no umbral: vuelve a disparar en el 10, 15, 20...). El test cubre 'recrea al quinto fallo' pero ni el techo de 30 s ni la periodicidad del módulo. Son constantes distintas de las del ErrorHandler (base 200/500 ms) y es fácil unificarlas por error al reescribir.
- EL MONITOR DE CONECTIVIDAD NO LEE NINGÚN REGISTRO: solo hace `ensureConnected()`. Con un socket TCP medio abierto el dispositivo figura CONNECTED indefinidamente — que es exactamente el agujero que RF25 (health real) tiene que tapar, y ningún test lo expone. Agravante: la rama que marca OFFLINE por `connectionTimeoutMs` es código muerto, porque `lastSeen` se setea a `Date.now()` dos líneas antes de compararlo contra el timeout, así que la condición nunca se cumple.
- RESET INCOMPLETO TRAS PASO CONFIRMADO = FATAL. En `executeStepCommand`, si el PLC confirmó el paso pero el reset de messageIn/messageOut no se completa, el error se marca `fatal = true`: no se reintenta, la orden va directo a ERROR. Es una decisión de planta deliberada (reintentar sobre un PLC con el registro sucio es peligroso) que no figura en ningún RF ni en ningún test, y que se pierde si alguien reescribe la clasificación de errores desde RF19.
- GRAMÁTICA DE locationCode, detalles sin test: el sufijo `L` se normaliza a `D` en `normalizeAction` (RF01 nombra [T|D|L] pero nadie fija que L≡D); la estantería es `[A-Z0-9]+` codicioso con la `A` literal como separador, o sea que el prefijo admite dígitos y el parseo depende de esa 'A'; el nivel se valida por charCode contra A..L (12 niveles); y `hasLocationActionSuffix` usa `/[TDL]$/i` sobre el string CRUDO, no sobre el parseo, así que rechazaría cualquier código que termine en esas letras aunque no sea una acción. Los tests solo ejercitan T y D sobre códigos bien formados.
- RANKING DE SLOT — dos detalles que la firma del código esconde: `positionPreferenceRank(source, candidate)` IGNORA su parámetro `source` y devuelve `candidate.position - 1`, es decir que la preferencia de posición es ABSOLUTA (1 antes que 2 antes que 3), no relativa al origen. El test sí lo pinea, pero la firma miente y un port que 'arregle' la función a distancia relativa rompe el ranking. Y el desempate final es `localeCompare` del locationCode normalizado — determinismo que ningún test fija y del que depende que dos ejecuciones elijan el mismo slot.
- LAYOUT FÍSICO DE LA ZONA DE PICKEO (src/config/pickSlots.js): los 12 slots reales del robot en producción, con su disposición concreta — módulo 02 solo posición 1 en los niveles A, C y E; módulo 01 posiciones 1, 2 y 3 en A, C y E. Solo niveles impares. Los fixtures de test usan 2 slots inventados, así que este layout no está cubierto por nada. `resolvePickSlotsConfig` además normaliza cada código a baseCode y deduplica por Set (silenciosamente), y la precedencia es options.pickSlots > PICK_SLOTS del entorno > default.
- COLA EXTERNA POR HTTP EN PRODUCCIÓN: el `.env` real dice `QUEUE_DRIVER=redis` y existe `src/core/queue/ExternalQueueManager.js`, un driver de cola que habla por HTTP contra un servicio externo. La spec dice 'Sin Redis/SQS' y no menciona este driver en ninguna parte, ni el mapeo de los 55 tests lo toca (todos los tests usan el driver memory). Hoy la cola del robot vive FUERA del proceso; si el cutover asume que siempre fue in-memory, se pierde ese hecho y con él las órdenes que estén en el servicio externo al momento del cambio. También queda sin cubrir el bug que la spec ya anota: `/api/devices/robots` devuelve `{}` en `queue` con este driver por una Promise sin await.
- PARÁMETROS MODBUS DE PLANTA sin test ni documentación: `unitId` por defecto 255 (no 1 — es lo que usan los Festo), puerto 502 y `timeoutMs` de socket 2000 ms, todos cableados como defaults en ModbusClient y ConnectionService. Además ModbusClient tiene su PROPIA cola interna de serialización (`ioQueue`) además del DeviceMutex de ConnectionService: son dos capas de serialización sobre el mismo socket, y el test de concurrencia solo prueba una. Si el port se queda con una sola, hay que saber cuál.
- `HTTP_PORT` está cableado en `src/server.js` como `const HTTP_PORT = 3000` e ignora la variable de entorno, que en el .env de planta también dice 3000. La spec ya lo anota como cambio, pero conviene registrar que hoy no hay ningún test que levante el servidor en otro puerto ni en otra interfaz, así que el bind a LAN de RF22 se va a estrenar sin red.
